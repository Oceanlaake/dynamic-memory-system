# 接口契约裁决（2026-10-17）

负责人：B / Retrieval
涉及方：A（Memory Schema）、B2（Dynamic State）、C（Web / Integration）

## 1. 背景

仓库里此前只有一份"整条链路返回格式"草案（`process/start.md`、`demo/DEMO_WALKTHROUGH.md`），没有模块级接口定义，且草案本身有若干自相矛盾之处。为避免 B1 / B2 / C 各自按不同理解开工，本记录冻结第一版契约。

**权威来源**：`APIs/memory_schema.json` 为 Memory 结构的唯一权威。`demo/` 下的产物仅作口头演示参考，不作为契约，也不修改。

## 2. 裁决

### 2.1 草案矛盾的处理

| # | 矛盾 | 裁决 | 依据 |
|---|---|---|---|
| 1 | 同一响应顶层键，一处 `question`、一处 `query` | 统一 `question` | 字段名用名词；`query` 是动作 |
| 2 | `effective_memories` 一处为 `string[]`、一处为 `{memory_id, role}[]` | 统一 `{memory_id, role}[]` | "起点/终点"类问题需要 `role` 才能展示推理过程 |
| 3 | `relations` 一处带 `reason`、一处不带 | `reason` **必填** | 前端需要展示判断依据，是项目核心卖点 |
| 4 | demo 有 `status` 字段，schema 没有 | **检索不感知状态** | schema 是权威；状态语义由 B2 用 `relations` 表达 |
| 5 | demo 用 `time.resolved_date`，schema 要求 `time.session_id` | 以 schema 为准 | 同上；demo 数据不修改，但也不用作测试输入 |

### 2.2 候选记忆的形态：内嵌完整 Memory 对象

```json
{ "memory": { "...完整 Memory..." }, "score": 0.95, "rank": 1 }
```

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 内嵌完整对象（采用）** | C 无需二次请求；B2 直接拿到 `time`/`evidence`；响应自包含，便于存证与回放 | 响应体积大；Memory 字段变化会传导到所有响应 |
| B. 只给 `{memory_id, score}` | 响应小；Memory 只有一个真源；传输层与数据层解耦 | C 和 B2 都必须再查一次；需要额外的批量查询接口；跨服务时是 N+1 |

**选择 A 的理由**：单机原型、6 个样本、条数在千级以内，体积不是瓶颈；减少一次往返换来 B2 与 C 的实现简化。若后续数据量增大，可在不改 `CandidateMemory` 结构的前提下增加 `?embed_memory=false` 之类的开关（暂不实现）。

### 2.3 `score` 语义

- 范围固定 `[0, 1]`，升序无意义，降序即排名。
- `bm25`：**本次查询内**的相对得分，最高分归一化为 `1.0`。
- `embedding`：cosine 相似度（实际值域约 `[0,1]`）。
- **不得跨查询比较分数**，这一点写进 schema 的 `description`。

### 2.4 `/api/retrieve` 与 `/api/query` 的关系

`query` 的 `candidate_memories` 与 `retrieve` 的 `candidates` 完全同构（同一 `$ref`），只有外层字段名不同（前者嵌在全链路响应里，后者是 `RetrievalResult`）。这样 B1 可以在 B2、C 未就绪时独立交付与评测。

## 3. B1 当前实现与已知局限

实现：`backend/retrieval/keyword.py`，纯 Python BM25（k1=1.5, b=0.75），零第三方依赖。

conv-30 上对 `How long did it take for Jon to open his studio?` 的实际排序：

| 排名 | memory | score | 是否回答问题所需 |
|---|---|---|---|
| 1 | `mem-conv30-002` 计划开工作室 | 1.0000 | 否（只说明目标） |
| 2 | `mem-conv30-004` 开业时间已定 | 0.3918 | **是（终点）** |
| 3 | `mem-conv30-005` 经营承压 | 0.3407 | 否 |
| 4 | `mem-conv30-003` 舞种偏好 | 0.0589 | 否 |
| 5 | `mem-conv30-001` 失业事件 | 0.0577 | **是（起点）** |

**这暴露了纯词法检索的硬伤**：`mem-conv30-001`（提供"起点时间"、答案必需）与问题几乎没有词汇重叠，被排到最后。若 `top_k=4`，Recall@4 = 0/1，答案将无法计算。

结论（写入后续计划）：

1. `top_k` 默认 5 时该样本可通过，但**不能把 BM25 当作最终方案**；
2. 下一步必须上 embedding 语义检索，BM25 退化为离线兜底与 hybrid 的一路；
3. 这也正好构成 proposal 中 "Vector RAG 对照实验" 的第一组基线数据。

> 更新（同日）：embedding 与 hybrid 已实现，对照结果见 `2026-10-17-检索策略选型.md`。R@4 由 0.50 提升到 1.00。

与 `demo/DEMO_WALKTHROUGH.md` 第 6 节手写分数（0.95/0.89/0.84/0.57，004 居首）的差异是**预期内**的：那组数字是人工编写的演示预期，本文档记录的是真实运行结果。演示时需明确区分。
