# 检索策略选型（2026-10-17）

负责人：B / Retrieval

## 1. 决策

| 项 | 决定 |
|---|---|
| 语义模型 | `sentence-transformers/all-MiniLM-L6-v2`（384 维，英文，约 90 MB，本地 CPU 可跑） |
| 默认策略（`DMS_RETRIEVER=auto`） | **hybrid**（BM25 权重 0.4 + embedding 权重 0.6） |
| 降级 | 未安装 sentence-transformers 或模型不可用时，`auto` 自动退回 `bm25` 并记 warning |
| 向量缓存 | `data/cache/embeddings/<model>-<fingerprint>.npz`，已加入 `.gitignore` |

选 `all-MiniLM-L6-v2` 而非更大模型的原因：LoCoMo 全英文、句子短、Memory 条数在千级；这个模型 CPU 上毫秒级，demo 现场不需要 GPU，也不依赖联网推理服务。

## 2. 实测对照（conv-30）

问题：`How long did it take for Jon to open his studio?`
答案所需的 Memory：`mem-conv30-001`（起点：失业后创业）、`mem-conv30-004`（终点：开业时间已定）

| 策略 | 排名 | R@1 | R@3 | R@5 | MRR |
|---|---|---|---|---|---|
| bm25 | 002, **004**, 005, 003, **001** | 0.00 | 0.50 | 1.00 | 0.50 |
| embedding | **004**, 002, 005, **001**, 003 | 0.50 | 0.50 | 1.00 | **1.00** |
| hybrid | 002, **004**, 005, **001**, 003 | 0.00 | 0.50 | 1.00 | 0.50 |

（加粗为答案所需记忆）

关键结论：

1. **BM25 的致命问题被修复**。`mem-conv30-001` 与问题几乎没有词汇重叠，纯词法时代排在最后；embedding 把它提到第 4 位，R@4 从 **0.50 → 1.00**。如果用 `top_k=4`，BM25 会漏掉"起点"，答案直接算不出来。
2. **单条 case 不足以判定 embedding 优于 hybrid**。两者 R@4 都是 1.0；hybrid 让 `002` 排第一（因为 BM25 认为字面重合最高的就是它），MRR 因此低于纯 embedding。排序差异不影响 K=4/5 的实际可用性，因此默认仍用 hybrid —— 它能同时兜住"精确名称/日期匹配"这类 embedding 容易漂移的查询。
3. 若演示时更看重 R@1，可临时 `DMS_RETRIEVER=embedding`。

**注意**：以上只有 1 个样本、5 条 Memory，指标波动极大，**不能作为选型依据**。等 A 交付 6 段对话的 Memory 后必须重跑 `evaluation/recall_at_k.py`。

## 3. 复现

```bash
pip install -r backend/requirements.txt

# 1) 从 LoCoMo qa + Memory JSON 自动生成用例
python -m evaluation.build_cases

# 2) 三种策略对照
python -m evaluation.recall_at_k --cases evaluation/cases/generated.json \
    --ks 1,3,5 --json-out evaluation/results/recall_generated.json

# 3) 扫融合权重
python -m evaluation.sweep --cases evaluation/cases/generated.json \
    --ks 1,3,5,10 --json-out evaluation/results/sweep_generated.json

DMS_RETRIEVER=embedding uvicorn backend.main:app --reload
```

首次运行会从 HuggingFace 下载模型到 `~/.cache/huggingface`（约 90 MB）。若网络受限，可预先在能联网的机器上下载后拷贝该目录，或设置 `HF_ENDPOINT` / `HTTPS_PROXY`。

## 4. 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `DMS_RETRIEVER` | `auto` | `auto` / `bm25` / `embedding` / `hybrid` |
| `DMS_EMBEDDING_MODEL` | `sentence-transformers/all-MiniLM-L6-v2` | 换模型会自动生成新的向量缓存 |
| `DMS_EMBEDDING_CACHE` | `data/cache/embeddings` | 向量缓存目录 |
| `DMS_MEMORY_DIR` | `data/memories` | Memory JSON 目录 |

`score` 语义：BM25 为本次查询内相对得分（最高 1.0）；embedding 为 cosine 相似度；hybrid 为加权和后截断到 `[0, 1]`。**不能跨查询比较**。

## 5. 评估管道与首轮数据（2026-10-17 补充）

### 5.1 用例自动生成

`evaluation/build_cases.py` 把 LoCoMo 的 `qa.evidence`（对话轮次）反查成 `required_memory_ids`：
memory 的 `evidence[].dia_id` 命中任一 `qa.evidence` 即算必需。已验证：自动生成的结果与手写的 conv-30 用例完全一致。

conv-30 的生成统计：

| 项 | 数量 | 说明 |
|---|---:|---|
| QA 总数 | 105 | |
| 跳过（category 5） | 24 | 对抗题，本身不要求召回 |
| **跳过（无 Memory 命中）** | **70** | **抽取覆盖不足，不是检索的错** |
| 生成用例 | 11 | |

⚠️ **70/105 = 67% 的 QA 找不到任何对应 Memory**。这是因为当前 `data/memories/conv-30.json` 只覆盖 12 个 turn（demo 规模）。A 的正式抽取管线必须覆盖绝大部分 turn，否则 Recall@K 无从评估、答案也无从生成。这一项需要 A 确认目标覆盖率。

### 5.2 首轮对照（11 个用例）

| 策略 | R@1 | R@3 | R@5 | MRR |
|---|---:|---:|---:|---:|
| bm25 | 0.318 | 0.818 | 1.000 | 0.624 |
| **embedding** | **0.455** | **0.864** | 1.000 | **0.727** |
| hybrid（0.4/0.6） | 0.409 | 0.818 | 1.000 | 0.705 |

### 5.3 融合权重扫描

| 词法权重 | R@1 | R@3 | R@5 | MRR |
|---|---:|---:|---:|---:|
| 0.0（=纯语义） | 0.455 | 0.864 | 1.000 | 0.727 |
| 0.2 | 0.318 | 0.773 | 1.000 | 0.644 |
| **0.4（当前默认）** | **0.409** | 0.818 | 1.000 | **0.705** |
| 0.6 | 0.318 | 0.818 | 1.000 | 0.644 |
| 0.8 | 0.318 | 0.818 | 1.000 | 0.629 |
| 1.0（=纯词法） | 0.318 | 0.818 | 1.000 | 0.624 |

`sanity check`：权重 0 与纯 embedding 完全一致，权重 1 与纯 bm25 完全一致，说明融合实现无偏差。

**结论与保留意见**：语义检索在这批问题上占优，词法权重越大越差；但 11 个用例、5 条 Memory、单一会话，**不足以据此改默认值**。当前保留 `0.4`，等 A 交付 6 段对话后重跑本节，再决定是否降到 `0.2` 或直接默认 embedding。

### 5.4 K 的取值

R@5 在所有策略下都是 1.000，R@3 已接近 0.86，说明 **K=5 够用，K=3 偏紧**。等数据量上来后重点看 R@3 与 R@5 的差距，以及 K 增大给 B2 带来的噪声成本。

## 6. 全量真实数据复测（2026-10-19）

A 的抽取管线交付后（`outputs/memories/`，10 个样本、4336 条 Memory），用自动生成的用例重跑。

### 6.1 用例覆盖

| 项 | 数量 |
|---|---:|
| QA 总数 | 1986 |
| 跳过（category 5 对抗题） | 446 |
| 跳过（无 Memory 命中） | **25**（1.3%） |
| 生成用例 | **1515** |

对比 5.1 节的 67% 缺口，抽取覆盖率已基本达标。每题的必需 Memory 数：均值 2.10、中位数 2、最大 29
（多证据综合题）。

### 6.2 三种策略（1515 个用例，检索 top-10）

| 策略 | R@1 | R@3 | R@5 | R@10 | MRR |
|---|---:|---:|---:|---:|---:|
| bm25 | 0.293 | 0.454 | 0.520 | 0.587 | 0.520 |
| embedding | 0.300 | 0.469 | 0.540 | 0.625 | 0.551 |
| **hybrid（0.4/0.6）** | **0.334** | **0.510** | **0.578** | **0.666** | **0.588** |

**hybrid 在全部指标上领先**，与 11 用例时"纯 embedding 最好"的结论相反——样本变多、记忆池从 5 条涨到
400+ 条后，词法的精确匹配开始产生正贡献。这也说明早期结论不可靠，必须用全量数据定论。

### 6.3 融合权重

| 词法权重 | R@1 | R@3 | R@5 | R@10 | MRR |
|---|---:|---:|---:|---:|---:|
| 0.0（纯语义） | 0.300 | 0.469 | 0.540 | 0.625 | 0.551 |
| **0.2** | **0.351** | **0.526** | **0.589** | **0.674** | **0.611** |
| 0.4（当前默认） | 0.334 | 0.510 | 0.578 | 0.666 | 0.588 |
| 0.6 | 0.318 | 0.491 | 0.555 | 0.638 | 0.564 |
| 0.8 | 0.306 | 0.473 | 0.536 | 0.613 | 0.542 |
| 1.0（纯词法） | 0.293 | 0.454 | 0.520 | 0.587 | 0.520 |

留出验证（dev = 8 个样本 / test = conv-49、conv-50，304 个用例）：

| 权重 | dev R@10 | test R@10 |
|---|---:|---:|
| 0.0 | 0.6429 | 0.5545 |
| **0.2** | **0.6881** | 0.6167 |
| 0.3 | 0.6882 | 0.6151 |
| 0.4 | 0.6782 | **0.6174** |
| 0.6 | 0.6504 | 0.5908 |
| 1.0 | 0.5996 | 0.5372 |

**结论**：0.2–0.4 是一片平坦区，dev 与 test 的排序互相矛盾（0.2 赢 dev、0.4 赢 test），差异在噪声范围
内。**保持默认 0.4 不变**，避免对单一测试集过拟合；若后续数据量继续增大，可重新评估。

### 6.4 K 的选择

R@3 → R@5 → R@10 的增益：hybrid 为 0.510 → 0.578 → 0.666，仍在上升，说明**单靠增大 K 无法解决
长尾**（大量题目需要 3 条以上证据）。建议：

- 默认 `top_k=5`，兼顾覆盖与 B2 的输入成本；
- 评测报告同时给出 R@5 与 R@10，并在 SRS 中说明差额来源（多证据综合题）。

### 6.5 性能修正

实测发现两处性能问题，已修复：

1. **BM25 每次查询都重建索引**：改为按 Memory 集合缓存，1515 用例的检索从分钟级降到秒级。
2. **SentenceTransformer 每次加载都联网校验**：网络受限时每个文件要重试 5 次、耗时数分钟。
   改为优先 `local_files_only=True`，仅当本地无缓存时才下载。修复后模型加载 5.3 秒，
   1515 个用例 × 3 种策略的完整评测耗时 **27 秒**。

同时评估脚本只取 `max(ks)` 个候选，不再为每题构造全量 `CandidateMemory` 对象。
