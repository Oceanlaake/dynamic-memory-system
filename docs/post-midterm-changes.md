# 中期之后改了什么：报告与 PPT 交接说明

更新：2026-10-31。读者：设计/需求报告同学、两位 PPT 同学、测试同学。

## 1. 一句话理解本次贡献

中期系统只能在已经召回的 Top-K 记忆中判断状态；后期增加了“根据初始候选识别主要状态槽位、补查同槽位历史、重新解析并解释证据是否足够”的可开关流程。
同时修正宽泛属性造成的部分伪冲突，并补齐来源追踪、证据状态、Web 展示和对照评测。
主要申报方向是 **规则驱动的自适应检索**。已经实现机制，但尚未证明最终问答 F1 普遍提高。

建议阅读顺序：本文件 → [最终测试交接](final-testing-handoff.md) → 自己负责的代码/结果链接。

中期 PPT 第 4 页把历史扩展列入需求/验收目标，第 10 页明确列为下一阶段方案；这不表示当时已经实现了扩展。

## 3. 中期与当前流程对比

中期：

```text
问题 → BM25/Embedding/Hybrid Top-K
     → 只在候选内部排序和判断关系
     → Effective Memory → 答案与证据 → Web
```

当前（开启 Bonus）：

```text
问题 → 原有 Retriever Top-K（排序算法未改变）
     → 识别受支持的问题类型、相关主体和主要状态槽位
     → 扫描该样本完整 Memory，补充同槽位历史
     → 去重、记录来源、检查新增数量上限
     → 一次状态关系解析与证据角色检查
     → Effective Memory / 拒答原因 → 答案、证据与扩展记录 → Web
```

关闭 Bonus 后直接使用初始 Top-K，但仍调用当前相同的 Resolver。
这用于隔离补检贡献；它不是自动还原整个中期旧解析器。因此实验有两种不同对照：

1. **当前开关消融**：相同新 Resolver，扩展关/开，判断补检本身的效果。
2. **中期与末期版本比较**：旧提交与最终提交分别运行，包含解析器等全部改动。

当前并不先运行一次完整 B2 再补检再跑 B2。槽位从初始候选直接提取，补检后只解析一次，避免无意义的重复调用。

## 4. 新增与修改的实际内容

| 变化 | 中期 | 当前实现 | 为什么要做 |
|---|---|---|---|
| 候选补检 | 固定 Top-K 后不再查库 | 单轮扫描同样本、同 `(subject, attribute)` 历史 | 修复正确种子已召回但状态历史被截断的问题 |
| 主要槽位选择 | 相关候选可能同时参与状态判断 | 属性词匹配优先，每个相关主体选一个主要槽位；持续时间可保留多个种子 | 避免其他属性干扰当前问题 |
| 动态问题触发 | 没有补检触发层 | 显式状态/时间词、偏好、居住地、变化、受支持的持续时间问法；普通 What is/does 不自动触发 | 避免普通事实题无必要扩展 |
| 集合型属性 | 同属性不同值易被当作冲突或替代 | plan/goal/venture/project 等宽泛集合不作为替代状态链扩展；不确定关系不强行建边 | “开工作室”和“希望选址在水边”可以是不同事实 |
| 真实矛盾保护 | 候选内相邻关系规则 | 仍检查明确对立/直接否定；集合内还检查非相邻的明确矛盾 | 防止去除伪冲突时同时丢掉真实冲突 |
| 空值相等 | 两边 value 为空可能被视为相同 | 不能仅因 null==null 判 RETAIN，还需有效相同值或内容确认 | 避免错误确认不同事实 |
| 变化问题输出 | 主要选择当前有效节点 | 有序、同槽位的历史节点可作为 state_history | 支持“发生了什么变化”的证据链展示 |
| 持续时间检查 | 已有双锚点演示 | 增加起止标记、同主体等保守检查 | 不因找到两个日期就编造时长；仍不是通用时间推理 |
| 扩展安全边界 | 无扩展 | 去重、最多新增 1–200 条、默认 50；确实截断时拒答 | 不丢掉初始候选、不对不完整闭包轻易作答 |
| 可解释输出 | 有关系理由与原始证据 | 增加候选来源、扩展槽位/ID、停止原因和独立证据状态 | 能回答“补了什么、为何没答、是否真的缺证据” |
| Web | 显示原始候选与状态链 | 补检开关、新增上限、初始/补检标签、执行摘要 | 用户和测试同学可直观对照 |
| 评测 | 原始检索与关系模块评测 | 三组消融、77 题探索、16 题原文核对诊断、成功/失败审计 | 将代码实现与实测结果对应起来 |

没有新增：抽取管线重构、新 Embedding 模型、Hybrid 融合算法、图数据库、通用多跳检索、Memory 压缩。
完整原始数据当前实际是 10 段、4,340 条 Memory；它们不是本轮新抽取出的成果。旧材料的 4,336/约 4,340 应按版本核对，不拿计数差异当成改进。

## 6. 新接口怎么解释

请求示例：

```json
{
  "sample_id": "conv-30",
  "question": "What is Jon's dance studio business status now?",
  "top_k": 5,
  "expand_slots": true,
  "max_expansion_memories": 50
}
```

| 字段 | 含义 |
|---|---|
| `expand_slots` | API 默认 false；Web 默认开启，可关闭重新提交作对照 |
| `max_expansion_memories` | 最多新增条数，不包含初始 Top-K；默认 50，范围 1–200 |
| `candidate_source` | initial / slot_expansion；初始排名保留，补检候选追加 |
| `expansion` | 初始数量、问题类型、选中槽位、新增 ID、是否截断、停止原因 |
| `evidence_status` | sufficient / insufficient / missing_anchor / missing_transition / conflict / unorderable 等 |

补检候选 `score=0` 只是接口占位，不是“相关度为零”或“置信度低”，前端显示“未计算相关度”。
停止原因和证据状态必须分开：没有新历史仍可能充分作答；扩展成功也可能仍缺锚点或存在冲突。
`not_comparable` 表示相关候选属于集合型属性，保留原候选；`no_seed` 表示没有相关状态种子；前者不等于证据一定不足。
持久化 Memory JSON 没有新增必填字段，没有 `entity/state_slot` 图索引，也没有实现任意历史时点的在线查询参数。

## 7. 已有实测结果，怎么用于报告/PPT

所有以下结果都属于开发探索/暂定诊断，不能代替最终独立测试集。

| 数据范围 / 方法 | 证据召回 | 平均候选 | 答案 F1 | 可说明什么 |
|---|---:|---:|---:|---|
| 77 道原始 QA，第一版 Hybrid 补检 | 55.09% | 4.17 | 0.119 | 直接广泛扩展有负收益 |
| 77 道原始 QA，当前 Hybrid Top-3 | 54.76% | 3.00 | 0.130 | 当前基线 |
| 77 道原始 QA，当前 Hybrid 补检 | 54.76% | 3.14 | 0.130 | 收紧后消除已知额外拒答，恢复基线，不是超越基线 |
| 16 道状态专项，Hybrid Top-3 | 65.63% | 3.00 | 0.330 | 针对性开发诊断基线 |
| 16 道状态专项，Hybrid 补检 | 93.75% | 6.00 | 0.294 | 状态历史召回改善，但答案质量仍有瓶颈 |

77 题的召回列是 Memory 级集合召回；16 题为原始证据轮次召回，两种粒度不能相互直接比较。
77 题 F1 分母为全部 77 道可评测题；16 题 F1 只针对 14 道可回答题，另 2 道单独检查拒答。
16 题中 4 道为课程原题、12 道为基于真实对话补写题，标注由 Codex 核对但未经独立人工验收；多题来自同一对话，不视为独立样本。
16 题的规则诊断 11/16 还包含一次因其他冲突“碰巧拒答”的情况，不要把它作为正式答案准确率。

本地工程验证由最初的 85 项增至当前 128 项后端测试，另有 8 项 Demo 检查和前端构建通过。
这表示覆盖了更多回归，不表示真实 QA 准确率为 100%。LLM 混合模式的末期完整评测尚未完成；本轮探索全部使用 rules。

结果来源：[第一轮](bonus-quick-test.md)、[第二轮修正](bonus-optimization-v2.md)、[16 题专项](state-diagnostics-test.md)。
最终报告主结果必须由测试同学按照 [最终测试交接](final-testing-handoff.md) 另行完成。

## 8. 两个可用案例

### 成功：补回当前经营困难状态

来源：16 题中的 `state-04`，截至 session_18 的完整历史。

- 问题：What is Jon's dance studio business status now?
- Hybrid Top-3 原先回答“准备开工作室”。
- 补检找回 `mem-conv30-256`：工作室经营困难、寻找投资人。
- 原文：D18:2；同一条原文还提及为覆盖开支而从事临时工作。
- 可以说明：相似度 Top-K 可能偏向过去的相关状态，槽位补检能把较新的有效证据补回来。

可用 [Hybrid 逐题 JSON](../evaluation/results/state_diagnostics/hybrid.json) 和 [原文审计](../evaluation/results/state_diagnostics/source_audit.json) 制作案例表。
该案例来自历史快照；若要复现 Web 截图，先加载相同快照，不能用默认 15 条 Demo 或完整 session_19 的界面假装同一次实验。

### 失败：就业历史找齐了，语义关系仍不够准确

来源：`state-03` / `change-01`。

- D1:2：Jon 失去银行工作；D18:2：后来为工作室开支做临时工作。
- 补检可以找到 `mem-conv30-257`，但 employment_status 混有失业回顾、创业意向和不同阶段的当前工作。
- 规则将其中部分事实判为冲突，导致无法回答最新就业情况。
- 可以说明：提高证据召回不自动等于提高答案质量；结构化槽位质量、事实时间和关系解析仍是关键限制。

持续时间的另一个限制是开业/录取节点可能 attribute 为空且缺少 effective_at，同槽位闭包不能自动解决。

## 9. 需求与设计报告同学的任务

建议更新既有 SRS/设计，不必把中期全部内容推倒重写：

| 部分 | 应补的内容 |
|---|---|
| 范围与需求状态 | 将“同槽位扩展”从计划改为已实现；将通用图/跨属性时间推理仍列为限制或未来工作 |
| 需求追踪 | FR-RET 对应补检与来源；FR-STS 对应关系/有效记忆/证据状态；FR-API/UI 对应开关与摘要；FR-EVL 对应正式评测与缺口 |
| 系统设计 | 插入 Query Orchestration/Slot Expansion 模块，说明与原 Retriever、Resolver 的边界 |
| 算法 | 问题类型 → 种子与主要槽位 → 同样本扫描 → 去重/上限 → 单次解析 → 证据检查 |
| 数据与接口 | Memory 持久化格式未重构；增加请求开关和响应 Trace/来源/状态字段 |
| 边界处理 | 无种子、集合属性、无新节点、截断、冲突、缺失锚点、无法排序 |
| 验收与实验 | 使用测试同学提供的正式结果；开发探索和工程回归另外注明 |
| 数据划分 | 修正现有 SRS 中“8+2”与课程“4+2”的口径，填入确认后的名单及真实历史使用情况 |
| 局限 | 未解决的就业语义、跨属性/空属性锚点、长答案及缺少统一 Full Text/Vector RAG 正式入口 |

Full Text/Vector RAG 的最终对照、课程动态题端到端准确率和正式测试集 F1 都不能提前标为完成。
需求与设计可以先写；实验数字待测试同学交付后统一填入。

## 11. 可直接使用的准确表述

> 中期系统已实现结构化记忆、混合检索和候选内部状态解析。末期新增查询驱动的状态槽位历史补检，使候选范围能够随初始证据调整，并记录新增来源、停止原因和证据充分性。针对性开发测试表明它能补回被 Top-K 截断的部分关键历史；最终答案仍受槽位语义、时间锚点和答案组织影响，需结合正式对照实验评价。

推荐贡献名称：**查询驱动的自适应检索：状态槽位历史补全**。

避免以下表述：

- “新建了完整 Graph Memory / 实现通用多跳搜索”：本轮没有图索引、路径搜索或跨实体遍历。
- “末期首次实现 Hybrid、DeepSeek、时间字段或原始证据展示”：这些中期已有。
- “Recall@5 提高到 93.75%”：该数字来自 16 题、初始 K=3 后的完整扩展集合，且是轮次级召回。
- “整体问答准确率提升”或“16/16 正确”：现有数据不支持，正式 F1 也尚待测试同学完成。
- “关系未输出就说明两条事实兼容”：不建边只表示规则没有确定关系。
