# Bonus 第一轮快速对照测试

日期：2026-10-31。

本页保留第一版的测试结果。后续代码修正与复测见 [第二轮优化记录](bonus-optimization-v2.md)。

## 结论

第一版的补检机制已经能运行，但在本轮真实抽取数据上尚未改善最终回答：
证据召回仅小幅增长，规则解析器遇到扩展历史后产生更多冲突拒答，答案 F1 下降。
现在可以说“实现了自适应补检机制”，不能据此说“显著提高了回答质量”。

## 数据与方法

- 只使用此前已用于开发和演示的 `conv-30`，没有将其他对话作为本轮调试集。
- 使用 `outputs/memories/conv-30.json` 的 280 条真实抽取 Memory，不使用 5 条人工演示 Memory。
- 原始 105 道 QA 中，排除 24 道 category 5 对抗题；其余 81 道中，4 道的证据未映射到任何抽取 Memory，最终评测 77 道。
- 77 道中有 76 道的全部原始证据轮次被抽取 Memory 覆盖，1 道只部分覆盖。
- 自动将引用 QA 标准证据轮次的所有 Memory 作为检索评分代理标注；它不等同于人工标注的状态链。
- QA 标准答案仅参与评分，不参与检索、补检或关系解析。
- 比较 Top-3、Top-10、Top-3 + 单轮同槽位补检，上限为新增 50 条。
- 同时运行 BM25 与 Hybrid；Hybrid 为 BM25 0.4 + all-MiniLM-L6-v2 Embedding 0.6，沿用现有默认阈值。
- 全部使用相同的 rules 状态解析器，不调用付费 LLM，不根据本轮结果修改优化规则。
- 本轮属于探索性检查，不是课程独立测试集结果，也不包含 Full Text / Vector RAG 的最终课程对照。

## 总体结果

“证据集合召回率”衡量最终候选集合覆盖了多少代理标注 Memory；扩展集合可超过 K，因此不将其统称为 Recall@3。
F1 使用本地英文 token 口径，不是答案准确率，也尚未对齐课程官方脚本。

| 检索器 | 方案 | 证据集合召回率 | 原始证据轮次召回率 | 平均候选数 | 答案 F1 | 拒答题数 |
|---|---|---:|---:|---:|---:|---:|
| BM25 | Top-3 | 52.38% | 60.61% | 3.00 | 0.142 | 2 |
| BM25 | Top-10 | 61.41% | 67.47% | 9.94 | 0.115 | 13 |
| BM25 | Top-3 + 补检 | 53.03% | 61.26% | 3.82 | 0.131 | 8 |
| Hybrid | Top-3 | 54.76% | 62.55% | 3.00 | 0.130 | 3 |
| Hybrid | Top-10 | 63.79% | 72.40% | 9.96 | 0.123 | 4 |
| Hybrid | Top-3 + 补检 | 55.09% | 63.20% | 4.17 | 0.119 | 9 |

Hybrid 补检相对 Top-3 的证据集合召回提升仅 **0.32 个百分点**，平均多 1.17 条候选，新增 6 道拒答。
两种检索器各只有 1 道题的代理 Memory 召回率提高；答案 F1 均为 0 道提高、75 道不变、2 道下降。
增大 K 虽提高证据召回，也没有改善平均答案 F1，说明瓶颈并不只在召回数量。

## 补检实际触发了哪些问题

当前问题规则将 77 道中的 63 道判为 factual、13 道判为 current_state、1 道判为 duration；没有 change 问题。
这只是系统分类，不是人工动态题标注，不能将这 14 道直接当作课程动态状态专项集。

- BM25：10 道加入了新 Memory，4 道没有更多历史，63 道不触发扩展。
- Hybrid：11 道加入了新 Memory，3 道没有更多历史，63 道不触发扩展。
- 无数量上限截断，本轮没有因上限触发拒答。

仅观察规则识别的 14 道问题时，Hybrid 的召回率从 53.57% 升到 55.36%，
平均候选从 3.00 增到 9.43；F1 从 0.137 降到 0.077，拒答从 1 道增到 7 道。
因此，全量 77 道上的小幅变化掩盖了扩展子集较明显的负收益。

## 失败案例与原因

### 1. 召回更多证据，未能形成更好的答案

BM25 的 “How long did it take for Jon to open his studio?”：
证据集合召回率从 0% 增至 50%，但扩展后出现 employment_status 槽位冲突，仍然拒答。
Hybrid 的 “What does Jon's dance studio offer?”：召回率从 0% 增至 25%，也因冲突未获得答案收益。

这说明“扩展能找到更多历史”与“扩展后的历史能被正确解析”是两个不同问题。

### 2. 原来包含答案，补检后误触发冲突

“What is Jon offering to the dancers at his dance studio?”：
Top-3 已回答一对一指导与训练，F1 为 0.400；补检后证据召回率仍为 100%，但答案变为 null，F1 降为 0。

扩展引入的 business_venture 历史中包括：

- `mem-conv30-003`：Jon 正在创办舞蹈工作室。
- `mem-conv30-016`：Jon 希望工作室选址在水边。

两者都来自 session_1，时间字段相同。当前规则把同槽位、不同 value、无法排序的节点判为 CONFLICT。
但上述事实可以同时成立，属性相同并不能证明它们属于互斥状态。

另一组为“经营工作室”与“寻找投资人”，同样被宽泛的 business_venture 属性合并。
问题 “What is Jon working on opening?” 也受到影响，F1 从 0.444 降至 0。

### 3. 动态问题触发条件过宽

`What is/does ...` 被广泛归为当前状态问题，其中包括工作室提供什么服务、纹身意义、开业情绪等事实问题。
部分题不需要完整状态历史，却扩展了 future_plan、anticipation 等宽泛属性，放大了冲突规则的误判。

## 对结果的解释边界

- 4 道完全没有映射 Memory 的非对抗题未计入本表；结果不能代表原始 81 道题的端到端表现。
- 本地答案生成经常直接返回 Memory 内容。标准答案可能只有 “contemporary”，即使返回句子包含该词，token F1 仍会较低；F1 的绝对值不等同于人工正确率。
- 两道负收益题原本包含回答信息，扩展后拒答，负收益并非仅由答案长短评分造成。
- 未提供人工关系/Effective Memory 标注，因此未报告这两项准确率，原始 JSON 中为 null。
- Hybrid 首题包含模型初始化/下载时间，Top-10 又复用了查询缓存。本轮耗时不适合做性能比较，因此不使用日志中的平均耗时宣称加速或减速。
- 缺少已确认的课程数据划分，这轮不能证明独立测试集的泛化表现。

## 下一轮优先修改

1. 收紧动态问题与种子槽位选择，不把所有 `What is/does` 问题及所有相关候选槽位都扩展。
2. 区分互斥状态槽位与可累积事实属性；business_venture、future_plan 等宽泛属性不能直接执行“不同值即冲突/替代”。
3. 把冲突限制在当前问题所需的证据上；补检引入的旁支事实不应自动否决已有答案，但也不能无条件忽略真实冲突。
4. 用真实 Memory 整理一组人工检查过的状态变化题，再判断是否需要受控别名或跨属性生命周期映射。
5. 保存本轮原始结果，后续修改先在开发数据验证，再冻结参数并运行独立测试集。

本轮仅增加评测与诊断代码，没有为了提高分数修改补检或状态解析规则。
