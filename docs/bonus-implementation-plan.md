# 后期 Bonus 实现与交付计划

更新日期：2026-10-31

## 目标与定位

以“查询驱动的自适应检索——状态槽位历史补全”为唯一主要 Bonus。
在现有 Top-K 检索之后，根据候选中的主体—属性槽位补充同样本历史，再执行状态解析。
设计依据见 [中期优化规划](state-evidence-chain-expansion.md)，课程要求见《项目要求大纲》第 10–13 页。
本计划中的实现状态以文末进度为准，不把计划能力写成已经完成的成果。

## 范围

- 单轮、规则驱动的槽位扩展；槽位键为去除首尾空格并忽略大小写的 `(subject, attribute)`。
- 只扩展与问题内容相关的种子；候选没有相关种子时不猜测槽位。
- 保留初始候选，按 memory_id 去重；限制新增候选数量，记录是否截断。
- 保留初始检索分数；补检候选不伪造相关度，使用 0 分及独立来源标记。
- 复用现有解析器；记录当前状态、变化、持续时间问题的证据充分性与停止原因。
- 查询接口提供开关；Web 可切换基线与补检模式，展示来源与执行结果。
- 不引入图数据库、通用多跳搜索、多轮 Agent、跨属性生命周期映射或压缩。
- 不支持任意历史时点查询；同槽位补全也不能自动找回不同属性下的时间锚点。

## 阶段一：代码与回归验证

1. 增加共享的问题相关性判断及查询类型识别。
2. 实现纯函数式同槽位补检模块，独立于具体 Retriever 和 LLM。
3. 接入 `/api/query`，同步 JSON Schema、Python 模型与 TypeScript 类型。
4. 增加证据检查：当前状态无未解冲突；变化问题需要同槽位、有序的前后节点；持续时间需要起止角色。
5. 扩展停止原因与证据充分性分别记录：“无新增节点”不能直接等同于“证据不足”。
6. 增加前端开关、候选来源和执行摘要。
7. 验证遗漏后继状态、无种子、去重、样本隔离、数量上限、冲突、缺失锚点及关闭开关后的行为。
8. 运行后端测试、Demo 校验与前端构建。

为避免无效的重复解析，第一版直接从初始候选提取槽位，补检后只调用一次关系解析器；
不先运行一次完整 B2 再运行相同 B2。槽位提取不依赖关系标签，不影响补全机制。

## 阶段二：评测

固定抽取数据、Retriever、Resolver、模型和参数，在同一批题上比较：

| 方案 | 目的 |
|---|---|
| 固定 Top-K + 状态解析 | 原系统基线 |
| 更大 K + 相同状态解析 | 检查收益是否仅来自更多候选 |
| Top-K + 同槽位补检 + 相同状态解析 | Bonus 消融实验 |

- 另保留课程要求的 Full Text、Vector RAG 对照。
- 使用课程指定的 4 段开发集、2 段独立测试集；先确认具体划分与官方动态题标注是否齐备。
- 开发集用于调参，冻结参数后评测测试集，不依据测试集失败修改规则再报告为独立测试结果。
- 专项题覆盖“正确种子已召回但历史遗漏”，同时报告全量题与无种子、无收益、负收益案例。
- 指标：原始 Recall@K、补检后集合证据召回率、状态关系准确率、有效 Memory 判断、答案 F1、候选数量、耗时、调用次数、拒答数。
- 补检后的候选数可超过 K，集合召回率不能继续标为原始 Recall@K。
- 新增可复用的三组对照入口；只有真实标注齐备后才能产出最终课程评测结论。
- 小样例和合成用例仅证明机制与回归正确，不能替代独立测试集实验。

## 第一版实现记录

- 核心模块：`backend/retrieval/expansion.py`；查询编排：`backend/query.py`。
- `/api/query` 新增 `expand_slots`（默认关闭）、`max_expansion_memories`（默认 50，表示新增条数）；Web 默认开启，并提供对照开关。
- 初始槽位从候选直接提取，单轮扫描后解析一次；不会为创建初始关系图额外调用一次 LLM。
- Python、JSON Schema、TypeScript 契约已同步；不修改持久化 Memory 数据。
- 共享解析器增加变化问题的有序历史输出、充分性原因及持续时间起止标记检查。三组评测均使用这个相同解析器，避免把解析器改进误算为扩展收益。
- 新增回归覆盖补回后继状态、冲突拒答、大小写与去重、无种子、样本隔离、上限、变化问题与持续时间锚点。
- 本地验证：后端 103 项测试通过；Demo 8 项检查通过；前端 TypeScript 检查及生产构建通过。前端仍有打包体积提示，本次不进行打包结构优化。

上述 103 项为第一版验证记录。第二轮增加通用槽位策略、真实冲突和非相邻否定等回归后，共 128 项测试通过；Demo 和前端构建仍通过。

### 评测入口

```bash
.venv/bin/python -m evaluation.slot_expansion \
  --cases evaluation/cases/conv-30.json \
  --memory-dir data/memories \
  --retriever bm25 --resolver rules \
  --top-k 1 --larger-k 5 \
  --json-out evaluation/results/slot_expansion_smoke.json
```

入口固定运行 `fixed_k`、`larger_k`、`slot_expansion` 三组，输出逐题结果和汇总。
`required_memory_ids` 必填，仅用于评分；可选标注为 `expected_effective_memory_ids`、`expected_answer`（允许 null）、`expected_relations`（from/to/relation）。
缺少对应标注时，准确率与 F1 输出 null，并附已标注样本数，不能将其解释为已经完成这些指标的实验。
答案 F1 当前采用英文小写字母数字分词并去除 a/an/the，是本地评分口径，尚未对齐课程官方评分脚本。
输出记录 Resolver 次数，不将其冒充 LLM 调用次数；耗时受到初始化和缓存影响，正式性能实验需另做预热及重复测量。

### 首次流程验证结果（不是课程最终实验）

使用 `data/memories` 的 5 条演示 Memory 和已有的 1 道持续时间题：

| 方案 | 候选数 | 证据集合召回率 | 是否作答 |
|---|---:|---:|---|
| Top-1 | 1 | 0% | 否 |
| Top-5 | 5 | 100% | 是 |
| Top-1 + 槽位补检 | 2 | 50% | 否 |

补检找回同槽位的开业节点，但未找回不同属性 `employment_event` 下的起点，因此仍返回 `missing_anchor`。
这个结果验证了预期边界，也说明不能用当前 Demo 宣称已解决跨属性持续时间问题。
专项回归中“Top-K 只含旧状态、补检找回新状态”的受控案例已通过；该案例也不能替代真实独立测试结果。
